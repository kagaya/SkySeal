# SkySeal v1.1 normative core

Status: reference implementation baseline
Version: 1.1.0-draft.1
Date: 2026-08-30

This document fixes the byte-level rules required for independently verifying a
SkySeal v1 commitment and its WebAuthn approval. The words MUST, MUST NOT,
SHOULD, and MAY are normative.

## 1. Privacy boundary

A public v1 seal MUST NOT contain a source file name, path, Google Drive ID,
revision ID, MIME type, file size, folder name, or file-to-hash mapping. Raw
WebAuthn credential IDs and user handles are also excluded from public
artifacts. A public seal necessarily reveals its ORCID identity, publication
history, and number of distinct hashes.

The plain hash set permits a known-candidate test: anyone who already has
candidate bytes can hash them and test membership. Preventing that test is not
a v1 property.

## 2. Hash-list commitment

The format identifier is `skyseal-sha256-set-v1`.

The exact bytes MUST satisfy all of the following:

1. The file is non-empty UTF-8/ASCII without a BOM.
2. Every record is exactly 64 lowercase hexadecimal characters followed by LF
   (`0x0a`).
3. CRLF, blank lines, comments, headers, and trailing spaces are forbidden.
4. Records are in strictly increasing bytewise lexicographic order.
5. Duplicate records are forbidden.
6. The final record has a final LF.

The list is an unordered mathematical set of distinct byte-sequence hashes. It
does not assert file names, ordering, directory topology, or multiplicity.

`subject_digest.value` is lowercase hexadecimal SHA-256 over the exact
hash-list bytes, including the final LF.

## 3. Seal payload

The payload MUST conform to
[`schemas/seal-payload-v1.schema.json`](schemas/seal-payload-v1.schema.json).
Its `schema` value is `urn:skyseal:seal-payload:v1`.

The payload is canonicalized with RFC 8785 JSON Canonicalization Scheme. The v1
schema intentionally permits only strings, objects, and an integer identity
version; floating-point values are forbidden. A verifier MUST reject duplicate
JSON member names, non-integer JSON numbers, and lone Unicode surrogates.

The WebAuthn challenge is the 32-byte value:

```text
SHA256(
  UTF8("SkySeal WebAuthn Challenge v1\0") ||
  JCS(seal_payload)
)
```

The payload `identity_state_digest` binds the assertion to the canonical
identity-activation proof. The server-generated `created_at` is informational.
Only a separately verified timestamp proof supplies independent time evidence.

The optional `private_ledger_commitment` is `sha256:<64 lowercase hex>` over
the JCS bytes of an owner-held
[`private-ledger-receipt-v1`](schemas/private-ledger-receipt-v1.schema.json).
When present it is covered by the WebAuthn challenge and signature. The receipt
itself MUST NOT be public. Its random 32-byte salt prevents the public digest
from acting as a direct dictionary commitment to predictable Drive names or
IDs. A verifier MUST treat the Drive name as descriptive and the Drive ID plus
candidate bytes as the authoritative private mapping.

## 4. WebAuthn assertion

The public bundle MUST conform to
[`schemas/webauthn-bundle-v1.schema.json`](schemas/webauthn-bundle-v1.schema.json).
Its `schema` value is `urn:skyseal:webauthn-bundle:v1`.

A verifier MUST NOT trust the RP ID or allowed origin merely because they occur
inside the bundle. They are verification hints. The verifier MUST receive the
expected RP ID and origin from a trusted local configuration or explicit
command-line arguments and require equality with the hints.

The verifier MUST:

1. decode `client_data_json`, `authenticator_data`, and `signature` as canonical
   unpadded base64url;
2. require `clientDataJSON.type == "webauthn.get"`;
3. require its challenge to equal the base64url encoding of the computed
   challenge;
4. require its origin to equal the trusted exact HTTPS origin;
5. reject a true `crossOrigin` value;
6. require `rpIdHash == SHA256(UTF8(trusted_rp_id))`;
7. require the User Present and User Verified flags;
8. resolve an active public key from the credential record named by
   `credential_event_digest`; and
9. verify the signature over
   `authenticatorData || SHA256(clientDataJSON)`.

Phase 0 supports ES256 (`alg = -7`) and Ed25519 (`alg = -8`). The public
credential key is represented as JWK in the signed identity history. Raw
credential IDs remain private routing data.

## 5. Identity genesis

The initial identity record MUST conform to
[`schemas/identity-genesis-v1.schema.json`](schemas/identity-genesis-v1.schema.json).
Its canonical JSON digest is `SHA256(JCS(identity_genesis))`, written as
`sha256:<64 lowercase hex>`.

For the initial credential, the genesis digest serves as the identity-genesis
digest and credential-event digest. After activation, the canonical digest of
`identity-activation.json` serves as the identity-state digest. Later
append-only credential events will advance only the state and credential-event
references.

The genesis file requires an authenticated ORCID iD, exact RP ID, initial public
key, recovery-code commitment, and the full pinned OpenPGP primary fingerprint.
The OpenPGP field is retained for compatibility with the already-created draft
v1 genesis and is optional identity-link metadata. Its presence is not proof of
key control, and an OpenPGP signature is not required by v1.1.

## 6. ORCID-bound Passkey identity activation

The public activation record conforms to
[`schemas/identity-activation-v1.schema.json`](schemas/identity-activation-v1.schema.json)
and has schema `urn:skyseal:identity-activation:v1`. Its payload has schema
`urn:skyseal:identity-activation-payload:v1` and contains exactly the identity
iD, identity version, canonical genesis digest, trusted RP ID, a random 32-byte
nonce encoded as canonical base64url, and a UTC creation timestamp.

The activation WebAuthn challenge is:

```text
SHA256(
  UTF8("SkySeal Identity Activation Challenge v1\0") ||
  JCS(identity_activation_payload)
)
```

A verifier MUST validate the authenticated ORCID format and genesis binding,
take the expected RP ID and exact origin from trusted configuration, require
User Present and User Verified, and verify the assertion with the initial
credential public key in the genesis. Bundle verification MUST require
`identity.identity_state_digest` and the signed seal payload's corresponding
field to equal `SHA256(JCS(identity_activation))`.

ORCID OAuth establishes which ORCID account authenticated to the service; the
public Passkey activation establishes control of the registered credential over
that exact ORCID-bound genesis. Neither claim alone is treated as the complete
SkySeal identity activation.

## 7. Time evidence

OpenTimestamps stamps the exact `.skyseal.json` bytes and the exact
`identity-activation.json` bytes. A verified timestamp establishes that the
target existed prior to the attested blockchain time. It does not establish an
exact creation time.

## 8. Legacy artifacts

Existing root-level SkySeal hash lists, OpenPGP signatures, and OTS proofs are
legacy artifacts. Their original byte sequences MUST NOT be normalized,
renamed, or rewritten. The strict v1 parser applies only to artifacts declaring
`skyseal-sha256-set-v1`.

## 9. Verification boundary

The reference verifier checks the strict hash set, payload binding,
identity-genesis and identity-activation digests, trusted RP/origin, WebAuthn
flags, and ES256 or Ed25519 signatures. The publication verifier additionally
checks the v2 manifest and OpenTimestamps proofs. Optional OpenPGP identity
links and credential events after genesis remain outside the v1.1 verification
claim.
